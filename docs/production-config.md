# Animate AV Runtime Config Hygiene

This public document describes what must stay out of the repository. It does not
list production values, private hosts, provider settings, Store Connect setup,
or release handoff details.

## Source Of Truth

Runtime values are generated by private AVALSYS tooling for maintainers. Do not
add checked-in `.env` files, example secret files, hardcoded production URLs,
signing values, provisioning profiles, or hand-written local config values to
this public repo.

The generated local file is:

```text
apps/ios/Config/Local.xcconfig
```

It is gitignored generated output. Regenerate it whenever switching local,
staging, or release environments.

For signed development workflows, use the generated `staging` config. AVALSYS
Apps AV product workflows should run against deployed preview in development,
not a local Wrangler worker, whenever they touch Account AV, media uploads,
credits, R2-backed artifacts, purchases, render jobs, or account deletion.
Animate AV development validation also uses Convex cloud `dev`, not a local
Convex runtime.

## Public Rules

- Keep committed xcconfigs free of production runtime values.
- Keep publishable client keys blank unless generated into local ignored config.
- Keep signing team IDs and provisioning values out of git.
- Keep backend URLs, provider configuration, purchase setup, promo codes, and
  reviewer access details in private docs.
- Use private release docs for App Store Connect, RevenueCat, pricing, privacy
  answers, and review notes.

## Validation

After generating local config, maintainers can validate effective build
settings with:

```bash
scripts/check-ios-runtime-config.sh --env staging
```

For TestFlight, App Store archives, or any signed-in production smoke, generate
the production local config first and validate the Release settings:

```bash
scripts/generate-ios-local-xcconfig.sh --env prod
scripts/check-ios-runtime-config.sh --env prod --configuration Release
```

Do not archive or upload a TestFlight build while this check reports `staging`,
preview hosts, local hosts, or a test Account AV publishable key. TestFlight
builds use the production bundle identifier and must use the matching
production Account AV environment. Use the private release runbook for the
remaining production archive and App Store Connect checks.

Do not treat auth failures from unsigned simulator builds as production auth
evidence. Signed-in flows require a signed install using the validated runtime
config. If an unsigned build was installed first, uninstall both development and
production bundle identifiers from the simulator before repeating the signed
smoke.

The checker should redact sensitive values and fail when local, preview, or
placeholder config leaks into a release build.

## Unsigned Builds

`CODE_SIGNING_ALLOWED=NO` is acceptable for compile checks and isolated tests
only. Authenticated account, purchase, upload, render, and deletion flows need a
normally signed simulator or device build.
